# ADR 0025 — The bazar by chat (Telegram bot)

- Date: 2026-10-01
- Status: accepted (built at the founder's request — **§3, §6 and §7 are choices the founder should confirm**)

## Context
The founder wants recording the bazar to be as easy as possible: the purchaser should not need the Purchases page at all. They text or speak the day's list into a chat app, get the list back, and confirm it into stock. WhatsApp is what bazar staff use, but it needs Meta business verification (ADR 0010, still pending); Telegram bots need nothing and cost nothing, so Telegram ships first and WhatsApp later on the same core. Live voice *calls* were rejected: the WhatsApp Calling API needs a real-time media server Vercel cannot host and is limited to large partners in 2026, and Telegram bots cannot take calls at all. Voice notes feel the same to the purchaser.

## Decision
1. **Linking.** The owner makes a one-time link for a person who may buy for a branch (owner, or that branch's purchaser) in Settings → Telegram and sends it any way they like. The link is `t.me/<bot>?start=<code>`; tapping it makes Telegram send the code to the bot, which connects that chat to that person (`chat_links`). The code is 122 random bits, stored only as a SHA-256 hash, single-use, and expires after 48 hours. A chat speaks for one person; `/stop` or the owner disconnects it. Private chats only: a group would show one person's prices to everyone.
2. **The bot acts as the person, never as the bot.** The webhook runs with the service role, but every write goes through a `chat_*` function that resolves the chat to its linked person and then acts as them for the rest of that transaction (`private.act_as`). So the existing checks apply unchanged: `can_access_branch_role(owner, purchaser)`, `confirm_purchase_draft`'s single use, and the audit log names the person. Removing someone from the team stops their chat at once.
3. **Draft → ✅ in the chat.** A message becomes a `purchase_drafts` row that moves nothing. The bot answers with every line (matched ingredient, quantity, price) and the total, with **✅ Add to stock** and **❌ Cancel**. *Confirm: a ✅ tap in the chat counts as the explicit human approval CLAUDE.md #4 asks for; it is the same person seeing the same list as on the web.* The ✅ confirms exactly the lines saved in the draft (built in SQL from the draft, not sent by the bot), and only if none is flagged; a flagged line gets no ✅, only the reason and "send it again". The purchase is dated the branch business day the list was sent, even when the tap comes after midnight.
4. **Reading the list: code first, AI second.** A typed list in the usual shape ("মুরগি ১০ কেজি ১৮০০", "murgi 10kg 1800", one item per line or comma) is read by a deterministic parser with no AI and no cost. Anything else — spoken number words, a rate per kg, free text — goes to the existing purchase extractor (ADR 0018 §6) when AI is on, or the bot shows what it could not read and the format to use. Neither ever multiplies a rate by a quantity (CLAUDE.md #1): a line without a total is flagged.
5. **Voice notes** go through the LLM gateway's new `transcribe`, which is plan-checked, cap-checked and costed per second like every AI call (ADR 0008, 0016). The transcript is shown back ("🎤 I heard: …") above the list. Audio is never stored, same as chit photos (ADR 0018 §6). Photos of the chit reuse the photo extractor.
6. **Speech provider: OpenAI `gpt-4o-transcribe` for now**, because it needs no new vendor. *Confirm after a real test:* a September 2026 Bangla benchmark (1,001 clips) put gpt-4o-transcribe at ~29% character error rate against ~7–8% for Sarvam and Soniox. The LLM extractor recovers some of that, but if real bazar voice notes read badly, switch the gateway's speech transport to one of those; nothing else changes. `STT_MODEL` and `STT_USD_MICROS_PER_MINUTE` are env (TODO verify the price).
7. **Development without a public URL.** `pnpm telegram:poll` long-polls Telegram and posts each update to the local webhook route with the secret header, so development runs the production path. Production: `pnpm telegram:webhook https://…`. The route answers Telegram at once and does the work in `after()`. *Confirm the Vercel plan's function duration covers a 5-minute voice note (maxDuration 120 s is set).*
8. **The webhook trusts only the secret** Telegram echoes in `X-Telegram-Bot-Api-Secret-Token` (compared in constant time); each update is handled once (`webhook_events`, keyed by bot id + update id). Nothing the person said is logged.

## Alternatives considered
- **WhatsApp first** — the right channel for Bangladesh, blocked on Meta verification; the `chat_channel` enum and every `chat_*` function already take the channel, so it is a second transport, not a redesign.
- **A signed JWT per purchaser** (the bot calling Supabase as the user) — cleaner in principle, but needs the project's JWT signing secret in the app, which newer Supabase projects no longer expose; acting as the linked user inside the service-role function keeps the secret out and the checks identical.
- **Confirm by replying "yes"** — ambiguous in a chat full of messages; a button carries the draft id.
- **Auto-record high-confidence lists** — breaks draft → approve.

## Consequences
- Purchasers never need the web app for the bazar; the owner still sees every purchase, confirmed in the purchaser's name, on the Purchases page, and drafts they abandon stay in "From photo or voice".
- New env: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_WEBHOOK_SECRET` (and `OPENAI_API_KEY` for voice and photos).
- **Revisit** the speech provider with real recordings; add WhatsApp as a transport once Meta approves.

## Amendment (2026-10-02): new items on a list
Blocking a whole list because one item is not in the ingredient list made the bot useless for a purchaser who buys something new. A line whose **only** problem is "not in the ingredient list" (unit and price present and readable) is now shown as 🆕 with the name as written, in the unit it was bought in (kg → g, litre → ml, pieces/dozen/হালি → pcs). The same ✅ tap that records the purchase first creates that ingredient — `chat_confirm_purchase_draft` (migration `20261013000001`), as the linked person, audited as `ingredient.create_from_chat`. Nothing is created before the tap or when the list is cancelled. A same-named item that appeared meanwhile is reused, never duplicated, and never against a different unit (the draft then needs fixing). The purchaser needs no ingredient-editing role; the owner renames, merges or sets a Bangla name later. Every other doubt (unclear name/quantity/price, no price, bad unit) still blocks. *Confirm: a purchaser may add ingredient names (not costs) through the chat.*
